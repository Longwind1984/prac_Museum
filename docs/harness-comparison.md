# 横向 vs 纵向 Agent Harness

> 一份独立短文，扩自 [Agent 体验设计 v0 §5.3](./agent-experience.md)。
> 适合放进作品集 README 顶部或简历项目描述。

---

## 引子

2026 年的当下，AI agent 的横向 harness 已经卷成红海——Claude Code / Cursor / Devin / ChatGPT Agent / Manus 都在追求"通用编程 / 任务 agent"。在这个生态位，"会接 LLM"或"做过 chatbot" 已经不能算是 differentiator。

我想在这里提出一个观察：

> **纵向 harness 才是真正的 PM 工作。**
> 它不是技术问题，是产品理解问题；它不被通用平台磨平，反而随着通用平台变强而变得更有价值。

下面 4 节展开。

---

## 一、横向 harness 解决了什么

通用 agent harness 解决的是与场景无关的基础设施：

- file context、tool use、code execution
- compaction、prompt assembly、retry logic
- safety filter、slash command、hook 系统
- subagent / multi-agent 编排

这些都是必须的，且一旦做出来就会被复用，边际成本递减。它们的设计者是工程师——基础设施视角。

但通用 harness 有一个隐含假设：

> **所有任务都是"用户提需求 → agent 完成"的请求-响应循环。**

在编程场景，这个假设几乎总成立——用户每一轮都有一个明确意图（"帮我修这个 bug"），agent 的工作是把意图变成代码改动。

在很多其他场景，这个假设根本不成立。

---

## 二、当假设不成立时：纵向 harness 必须自己设计

举一个真实的例子——博物馆智能导览，这是一个**主题知识对话**场景：

- 用户在物理空间内移动
- 多数轮次**没有任何用户输入**（用户在看文物）
- agent 必须自决是否行动
- 默认行动是"什么都不做"
- 跨次记忆是核心资产（跨月、跨年时间尺度）
- 引用错一篇论文 = 信任崩塌

通用 harness 对这些都没有现成答案。每一条都需要纵向设计：

| 维度 | 通用 harness 默认值 | 主题知识对话需要的 |
| --- | --- | --- |
| 用户输入频率 | 每轮都有 | 多数轮没有；agent 自决 |
| Agent 主动性 | 默认主动 | **默认沉默** |
| 工具语义 | 确定性（读文件、跑命令） | 模糊检索（RAG / 记忆相似度） |
| 失败处理 | 重试 / 让用户重试 | **静默或降级**，不重试 |
| 上下文范围 | 单次会话 | 跨次（月、年） |
| Hallucination 容忍 | 中等（用户会发现并纠正） | **零**（引用必须精确验证） |
| 终止条件 | 任务完成 | 无明确终止 |
| 成功标准 | 任务正确性 | 关系累积 + 表现克制 + 信任沉淀 |

把这 8 条翻译成具体代码 = 这个产品的 harness。每一条都不是通用 SDK 能给你的，都是 PM 要做的设计决定。

---

## 三、纵向 harness 的设计就是 PM 的设计

来看几个具体的设计抉择——它们都不是工程上的"难"，是 PM 上的"敢"。

### 抉择 1 · SILENT 是状态机的默认叶子节点

在我设计的博物馆 agent 里，选模式决策树的**默认叶子节点是"SILENT"**——当没有任何分支匹配时，agent 什么都不做。

这不是 fall-through bug，是设计选择。它对应一个 PM 洞察：

> 用户来博物馆不是来找 agent 聊天的，是来看文物的。agent 在多数时刻的正确行动就是不行动。

通用 harness 默认的"行动"是 "继续生成下一步建议"。我的纵向 harness 默认的"行动"是 "保持沉默"。这一个翻转，需要的不是技术，是 PM 对场景的判断。

### 抉择 2 · 锚点验证器

M-04 跨次记忆主动开口模式（产品的杀手时刻）有一条硬规则：

> AI 主动开口的内容必须包含 ≥ 2 个具体细节（馆名 / 时间 / 停留时长 / 用户原话），且每个细节必须能在 memory payload 里**精确字符串匹配**。任何一条不通过 → **静默**，不降级。

为什么不降级？因为跨次记忆的 wow 时刻容不下"差不多就行"——一旦用户察觉造假（"你说我三年前停了 11 分钟，可我根本没去过那次"），整个产品对用户的信任就没了。**宁可不发声**，也不能让一次造假毁掉飞轮。

通用 harness 的 hallucination 处理通常是"加 disclaimer"或"让用户验证"。我的纵向 harness 的处理是"精确字符串匹配 + 失败即静默"。这条规则之所以成立，是 PM 对 "这个具体场景里 hallucination 的代价是什么" 的判断。

### 抉择 3 · 预热（eager fetch）

物理空间下用户不会等"agent 思考一下"。所以 harness 在用户进入新展厅的瞬间，预先拉取可能被看的前 5 件文物的 RAG context 到 session 缓存。等用户停下时，prompt assembly 几乎是 0 latency。

通用 harness 不假设"latency 要趋零"——它假设用户在等。我的 harness 必须假设用户不在等。这又是一条来自场景理解的设计。

### 抉择 4 · Citation 验证器

M-07 学界争议引述模式中，所有引用必须含**四要素**（作者 + 年份 + 著作 + 核心观点），且每一条必须能在 RAG 返回的 retrieved_context 里精确匹配。任何要素缺失 → 整段输出丢弃，退化为兜底句 "具体争议我得查一下，今晚发你"。

为什么这么严？因为引用一条编造的论文会被业内人当面打脸，损害的是产品自己的可信度，不是馆方的。**0 容忍**这条规则，是 PM 对"用户群里有真专家"这件事的认知。

## 四、对 AI PM 的含义

简历上写"会接 LLM"或"做过 chatbot"已经没有 differentiator——这些会成为 2027 年所有 PM 的基础能力。

现在的 differentiator 是：

> **会为一个具体场景设计 agent harness。**

具体表现：

1. **识别一个场景的独特约束**（用户输入频率、主动性默认值、工具语义、失败代价、上下文范围、hallucination 容忍）
2. **为这些约束设计具体的 agent loop / 模式池 / 工具调度 / 验证器**
3. **把场景洞察一路落到 prompt 级别的硬约束**（≤ 多少字、必须含 X、不能 Y、失败时怎么降级）
4. **把硬约束翻译成度量**（每一条规则对应一个目标指标）

横向 harness 的设计者是工程师，由公司主导；纵向 harness 的设计者是 PM，由个人主导。**这是 AI PM 在生成式时代最大的 leverage——它不会被通用平台磨平，反而会随通用平台变强而变得更有价值。**

类比：

- 横向 harness 像操作系统
- 纵向 harness 像针对该 OS 的某一类专业软件（CAD / Pro Tools / Bloomberg Terminal）

操作系统赢家通吃，专业软件按场景永远有空间。横向 agent harness 会高度集中（最终 1-3 家），但每一个值得做的场景都需要自己的纵向 harness——而每一个纵向 harness 都需要一个真正懂场景的 PM。

## 五、这份作品集试图证明什么

我做这份博物馆智能导览的 PRD + Agent 体验设计，**不是要证明我会做 chatbot**。我要证明的是：

> 我能为一个**不是编程、也不是闲聊的中间地带场景**，端到端设计完整的 agent harness——从场景洞察 → 状态机 → 模式池 → prompt 验证器 → 度量。

具体来说，本作品集展示：

| 设计层 | 产出 |
| --- | --- |
| 场景洞察 | PRD §2 范式批判 / §3 用户研究 / §5 竞争分析 |
| 产品哲学 → 可审计机制 | PRD §6.4 人格工程化 + §8.2 设计 6 条 + §9 reject list + §11.2 反指标 |
| 模式池 | Agent 体验设计 §3：8 个命名模式 |
| Prompt 验证器 | Agent 体验设计 §3.10 M-04 / §3.11 M-06 / §3.16 M-07 的完整 prompt + 验证器 + 失败兜底 |
| 状态机 | [`state-machine.md`](./state-machine.md) — XState 形式化 |
| Harness 哲学 | 本文档 |

每一层都不是抽象的哲学宣言——它们互相咬合：哲学（克制）→ 设计 6 条（默认低亮）→ 反指标（AI 主动 ≤ 用户主动 / 2）→ 状态机（SILENT 默认叶子）→ Prompt（M-04 字数 / 锚点验证）→ 度量（anchor_verification_pass_rate ≥ 95%）。

这不是技术 demo，是 PM 思维 demo。

> 技术由 Anthropic / OpenAI / Google 提供。
> 纵向 harness 由 PM 提供。
> **这是一个属于产品经理的、不被通用平台磨平的工作。**
