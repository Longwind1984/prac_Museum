# Agent 体验设计 v0

> 这份文档与 [PRD v1](./PRD.md) 平级。
>
> **PRD 回答的是**：这是一个什么产品，为谁做，不做什么，为什么这样做。
> **本文档回答的是**：AI agent 在每一轮收到输入后，**怎么主导**这场对话——选什么模式、拼什么 prompt、调什么工具、信息分几层、追问长什么样。
>
> 换句话说，PRD 把哲学说清楚了（克制 / 立场 / 记忆 / 对等），但**编排层是空的**：agent loop 长什么样、模式怎么调度、prompt 怎么组装、harness 与通用 LLM 应用有何不同——这一层在 PRD §6.4（人格 spec）和 §7.4（状态机）之间是断的。本文档把这层补上。

## 1. 为什么需要这份文档

PRD v1 写完之后，盘了一下断层：

| 已有 | 章节 |
| --- | --- |
| 人格 spec（system prompt 骨架 + 6 条话术 enforcement + 回归测试 8 条） | §6.4 |
| 14 个用户故事触点（一日剧本） | §7.2 |
| 6 维状态机 + 主动开口门槛函数 + 长程承诺记账 | §7.4 |

| 没有 | 这层叫什么 |
| --- | --- |
| 把 14 个触点抽象成的可复用模式池 | 交互模式库 |
| Agent 每一轮的决策循环：感知 → 选模式 → 调工具 → 生成 → 后过滤 | Agent Loop |
| 上层编排：上下文管理、工具调度、模式分派 | Harness |
| Prompt 的真实形态（不是模板示意，是带 few-shot 的完整 prompt） | Prompt Spec |

**编排层是 AI PM 显功力的位置**——它显示的不是哲学，是"我知道一个 agent 在垂直场景里到底怎么跑"。本文档把这一层做出来，且对其中 2 个最有代表性的模式（T5 跨次记忆主动开口、T7 四卡观点对照）做深抠：写出完整 prompt 结构 + few-shot + 后过滤规则 + 失败兜底。

## 2. 选题立场：博物馆智能导览 = 主题知识对话

简历"为什么选这个题"的回答应该是一句话：

> 博物馆智能导览是一个**主题知识对话场景**——长程、有上下文、有人格、有节制——介于娱乐性闲聊（查天气、讲笑话）和编程任务（well-defined task + 富工具）之间。它本来就需要自己的 agent harness：通用聊天 LLM 接个 system prompt 做不出来，通用 Agent SDK 也不够用。把这个 harness 设计出来，是这个项目的核心 PM 价值。

三类对话的 harness 需求对比：

| 维度 | 娱乐性闲聊 | 主题知识对话（本产品） | 编程任务（Claude Code） |
| --- | --- | --- | --- |
| 时间跨度 | 一次会话内（≤ 10min） | 单次参观 2h + 跨次月级累积 | 单任务内（不定，可达小时级） |
| 用户输入频率 | 高，每轮都有 | **极低，用户可以 30 分钟不开口** | 中，按任务进度推进 |
| Agent 主动性 | 被动响应 | **主动 + 被动混合，且主动有严格门槛** | 主动（提议下一步） |
| 工具 | 几乎无 | 跨次记忆、RAG、长程承诺队列、状态感知 | 文件读写、代码执行、shell |
| 终止条件 | 用户离开 | **无明确终止**（参观结束只是当前会话结束） | 任务完成 |
| 成功标准 | 用户满意度 | 用户感到陪伴 + AI 表现克制 + 记忆资产累积 | 任务正确完成 |
| 错误代价 | 低（讲个冷笑话） | **中**（破坏关系、显得话痨、断代错误冒犯专业用户） | 高（删错文件、跑错命令） |

**本产品 harness 的独特挑战**：

1. **主动性门槛**：Claude Code 几乎总是被请求的；本产品的 agent 必须自己决定每一轮是否开口。"决定不开口"和"决定开口"是同等成本的决策。
2. **极长上下文**：参观历史可跨年累积，传统 context window 装不下。需要分层记忆系统（短期 / 会话期 / 长期）。
3. **模糊工具**：RAG 和记忆召回不是确定性查询，是语义检索；命中质量直接决定输出质量。
4. **非阻塞节奏**：用户在物理空间移动，agent 不能让用户"等响应"。所有计算必须在用户掏手机之前预热完毕。

下面三层（模式库 → Flow → Harness）就是对这四个挑战的回答。

## 3. 第一层 · 交互模式库（Substrate）

把 PRD §7.2 的 14 个触点抽象为 **8 个命名模式**。每个模式是一张「模式卡」，含 7 个字段：

| 字段 | 说明 |
| --- | --- |
| 触发条件 | 在 6 维状态 + 用户动作下什么时候启用 |
| 信息层次 | 这个模式向用户展示几层信息、按什么顺序 |
| 输出形态 | 屏 / 语音 / 卡片 / 静默 / 触觉 |
| Prompt 骨架 | system 哪几句、检索注入在哪、few-shot 例子 |
| 追问入口形态 | 用户怎么继续——emoji / 切卡 / 长按 / 沉默等待 / 文字 / 语音 |
| 输出长度上限 | 字数 / 卡数 / 时长 |
| 反例 | 这个模式被滑成什么样就 fail 了 |

### 3.1 模式卡总览

| # | 模式名 | 对应 PRD 触点 | 信息层次 | 主导方 | 是否深抠 |
| --- | --- | --- | --- | --- | --- |
| M-01 | 克制式入口（recognition） | T1, T2 | 1 层 · 极简识别 | Agent 极轻一次 → 沉默 | – |
| M-02 | 先反问再亮观点（first-turn） | T3 | 2 层 · 承接 → 立场 | 用户输入 → Agent 短回 | – |
| M-03 | 拒讲完 + 长程承诺（defer-and-promise） | T4 → T12 | 2 层 · 拒讲 + 延期 | Agent 拒讲，承诺持久化 | – |
| M-04 | 跨次记忆主动开口（unprompted-from-memory） | T5, T14+30d | 1 层 · 主动一次 | **纯 Agent 主导** | ✅ 深抠 §3.10 |
| M-05 | 合上手机 · 反向推开（physical-defer） | T6 | 1 层 · 推开 + 反问 | Agent 推开 → 用户输入 → Agent 短回 | – |
| M-06 | 四卡观点对照（layered-disclosure） | T7 | **4 层 · 用户 / 馆方 / AI / 学界** | 用户触发，Agent 展开 | ✅ 深抠 §3.11 |
| M-07 | 学界争议引述（scholarly-supplement） | T9 | 2 层 · 馆方先 + 学界补 | 用户问 → Agent 答 | – |
| M-08 | 离馆收束（session-close） | T10, T13, T14 | 1 层 · 静态总结 | Agent 主导，无追问 | – |

8 个模式不是穷举——是把 PRD 14 个触点抽出来的"原子动作"。一次参观就是这 8 个模式在 6 维状态下的不同组合 + 重复触发。

### 3.2 M-01 · 克制式入口（recognition）

合并自 T1（入馆识别）和 T2（被动入口）。

| 字段 | 内容 |
| --- | --- |
| **触发条件** | `Location: Outside → Hall:X` 转换 OR 用户主动 pickup gesture |
| **信息层次** | 单层：识别已发生，提供极轻入口 |
| **输出形态** | 锁屏轻通知（无声、无横幅）+ 锁屏 widget（低对比度） |
| **Prompt 骨架** | 不需要 LLM——纯规则触发：模板字符串 + 当前展厅名 |
| **追问入口形态** | 锁屏 widget 上一个不发光的「你怎么看」按钮，**只在抬手识别触发时显现** |
| **输出长度上限** | 通知 ≤ 12 字；widget 内 ≤ 8 字 |
| **反例** | 全屏弹窗欢迎页、横幅推送、自动播放语音、震动 |

**机制点**：这个模式刻意**不调用 LLM**。recognition 是规则的活，让 LLM 介入只会拖慢响应、引入幻觉、且把"克制"变成"努力装克制"。

### 3.3 M-02 · 先反问再亮观点（first-turn）

| 字段 | 内容 |
| --- | --- |
| **触发条件** | 用户主动通过 M-01 入口 OR 文字 / 语音输入第一句 |
| **信息层次** | 2 层：先共情承接（卡 1），再给立场（卡 2） |
| **输出形态** | 两张连续卡，黑底，单句，自动切换 / 用户上滑 |
| **Prompt 骨架** | system: 人格 + 当前文物 retrieved_context；instruction: "用户原话 → 用 ≤30 字承接（不复读用户） → 用 ≤50 字给一句你自己的观察"  |
| **追问入口形态** | 卡 2 角落「我的看法」标签——按下进入 M-06（四卡对照） |
| **输出长度上限** | 卡 1 ≤ 30 字；卡 2 ≤ 50 字；总 ≤ 80 字（与 §11.2 反指标一致） |
| **反例** | "您好，这是一件……"（导览员腔）；"绝绝子！"（KOL 腔）；一段话说完不分卡（信息不分层） |

**信息分层的具体落法**：卡 1 是"我听见你了"（社交确认），卡 2 是"我有自己的判断"（专业内容）。两层必须**视觉分离**——不能是一段话用句号断开。这是把"先反问再亮观点"从话术准则落到 UI 节奏的关键。

### 3.4 M-03 · 拒讲完 + 长程承诺（defer-and-promise）

| 字段 | 内容 |
| --- | --- |
| **触发条件** | 用户问大问题（语义检测：含"区别""演变""谱系""为什么"） AND 当前位置不在最佳教学件前 |
| **信息层次** | 2 层：拒讲 + 延期承诺 |
| **输出形态** | 短句 + 浅按钮「对照件提醒」 |
| **Prompt 骨架** | 见 §3.4.1 |
| **追问入口形态** | 「对照件提醒」按钮（允许 / 不需要）；不允许在当前位置追问下去 |
| **输出长度上限** | ≤ 60 字 |
| **反例** | 真的展开讲完；只拒讲不承诺（让用户挂着）；承诺了不记账（永远不兑现） |

#### 3.4.1 M-03 prompt 骨架

```
[SYSTEM]
{人格基础块 from §6.4.1}

[STATE]
当前位置: Hall:佛造像
当前文物: 北魏石灰岩造像 (artifact_id=a-001)
对照件目标位置: Hall:佛造像, artifact_id=a-014 (北魏菩萨立像)
对照件距离: ~25m
长程承诺队列: []

[INSTRUCTION]
用户提出了一个跨件的对照问题。你不能在当前位置展开——展开会把后续对照场景的张力提前消耗掉。
任务：
1. 用 ≤ 60 字承认问题好 + 拒讲完。
2. 提示对照场景"一会儿到了再聊"。
3. 输出一个 promise 对象，给上层 harness 加到承诺队列。

[INPUT]
"北魏早期和晚期的区别从哪看？"

[OUTPUT FORMAT]
{
  "speak": "...",
  "promise": {
    "topic": "...",
    "fulfill_when": "Location == Hall:佛造像 AND CurrentArtifact.id == a-014",
    "fulfill_pattern": "M-02-or-custom-comparison",
    "expires_after_visit": true
  }
}
```

承诺记账由上层 harness 持久化（见 §5.1），不在本模式内做。

### 3.5 M-05 · 合上手机 · 反向推开（physical-defer）

| 字段 | 内容 |
| --- | --- |
| **触发条件** | 用户主动按下卡片角落的「合上手机看 30 秒」按钮（仅用户触发，agent 不推荐） |
| **信息层次** | 1 层在前（推开） + 1 层在后（反问） |
| **输出形态** | 屏幕全黑 + 倒计时角标 → 30 秒后柔光 → 单句反问 |
| **Prompt 骨架** | 推开阶段：纯规则；反问阶段：LLM 生成 ≤ 30 字反问，必须以"看清了什么"开头或类似引导观察的句式 |
| **追问入口形态** | 反问后用户文字 / 语音 / emoji 输入 |
| **输出长度上限** | 倒计时 30s；反问 ≤ 30 字 |
| **反例** | 倒计时期间还有其他 UI 元素；30 秒后跳出"你按了这么久"成就感反馈；反问变成"还要看吗？" |

### 3.6 M-07 · 学界争议引述（scholarly-supplement）

| 字段 | 内容 |
| --- | --- |
| **触发条件** | 用户问断代 / 风格归属 类问题 AND RAG 检索命中 `is_disputed=true` 字段 |
| **信息层次** | 2 层：复述馆方判断（不挑战）+ 补学界异见（带具体引用） |
| **输出形态** | 短句（语音耳机模式）或两张窄卡（屏模式） |
| **Prompt 骨架** | 见 §3.6.1，强制结构 |
| **追问入口形态** | "要不要我把那篇论文留给你今晚看？"——存到今日记忆卡（跨设备延续） |
| **输出长度上限** | 复述 ≤ 30 字；学界异见 ≤ 80 字（必须含作者 + 年份 + 著作 + 核心观点四要素） |
| **反例** | "我觉得馆方写错了"（挑战姿态）；"两份论文意见相左"（无具体引用）；编造论文（任何幻觉） |

#### 3.6.1 M-07 prompt 骨架

```
[SYSTEM]
{人格基础块}
你在引述学界异见时必须满足"四要素"：作者 + 年份 + 著作 + 核心观点。
任何要素缺失 → 不要引述，直接说"具体争议我得查一下，今晚发你"。

[STATE]
当前文物: a-027 (无标签造像，馆方标注"北齐")
RAG 命中 is_disputed=true: 是
RAG 检索结果:
  - {paper: "李静杰《北朝—隋唐造像样式的传承与转变》", year: 2018, source: "故宫博物院院刊", view: "衣纹褶子密度更接近北周"}

[INSTRUCTION]
按 M-07 模式输出。必须先复述馆方判断，再引学界异见。

[OUTPUT FORMAT]
{
  "speak": "...",
  "follow_up_offer": "要不要我把那篇论文留给你今晚看？",
  "memory_card_payload": {paper_id, save_for: "tonight"}
}
```

### 3.7 M-08 · 离馆收束（session-close）

合并自 T10（疲倦节律建议）、T13（今日记忆卡）、T14（离馆后回响）。

| 字段 | 内容 |
| --- | --- |
| **触发条件** | (a) Fatigue → tired AND Dwell < 30s 持续 ≥ 10min；OR (b) Location: Hall:X → Outside；OR (c) 用户首次打开离馆后界面 |
| **信息层次** | 单层静态总结（不可滚动） |
| **输出形态** | 一张静态卡 + 一个"我有新的想法"按钮 |
| **Prompt 骨架** | 半模板半 LLM——结构（停留 Top3 / 用户原话 / 未尽事项）是模板，每条内容由 LLM 从会话状态摘要 |
| **追问入口形态** | 「我有新的想法」按钮 → 用户向 AI 补记忆（这是反向流） |
| **输出长度上限** | 总长 ≤ 200 字；未尽事项 ≤ 3 条 |
| **反例** | 分享按钮；徽章；"今日逛馆评级 ★★★★"；自动跳转到下次推荐 |

> M-04 和 M-06 见 §3.10 / §3.11 深抠版。

### 3.8 模式之间的组合关系

8 个模式不是孤立的，它们之间有时间因果关系：

```
[ M-01 入馆 ]
       ↓ 用户主动
[ M-02 first-turn ] ←─── 用户触发「我的看法」 ───→ [ M-06 四卡 ]
       │                                                  │
       ↓ 用户追问大问题                                    ↓ 卡 4 学界争议
[ M-03 defer+promise ] ──────────────────────→ [ M-07 学界引述 ]
       │                                              │
       │   { promise 在状态机里 pending }           { 论文存今日记忆卡 }
       │
       ↓ 用户在对照件位置触发
[ M-03 兑现 → M-02 变体 ]
       ↓
[ M-05 合上手机 ] ← 用户随时可触发
       ↓ Memory == warm 触发
[ M-04 跨次记忆主动开口 ] ← 全场仅打破沉默的合法路径之一
       ↓
[ M-08 离馆收束 ] ── { 反向补记忆 } ──→ [ 写回长期记忆 → 下次 M-04 输入 ]
```

这张图是"flow 视图"的雏形，详见 §4。

### 3.9 模式与人格 enforcement 的咬合

每个模式都要走 §6.4.2 的 6 条 enforcement 触点。模式只决定"做什么"，enforcement 决定"以人格的方式做"：

| 模式 | 最依赖的 enforcement |
| --- | --- |
| M-02 | 准则 1（自称）+ 准则 3（节奏：先反问）+ 准则 4（立场词） |
| M-03 | 准则 3（节奏：拒讲完是节奏的体现）|
| M-04 | 准则 6（自暴露）+ 准则 5（诚实：锚点必须真，不能编） |
| M-06 卡 3 | 准则 4（"我倾向"开头）|
| M-06 卡 4 | 准则 5（学界争议必带引用，幻觉零容忍） |
| M-07 | 准则 5 同上 |
| M-08 | 准则 1 + 准则 2（句式短） |

即：模式 = "做什么"层，准则 = "怎么做"层。两层都过才输出。

### 3.10 深抠模式 A · M-04 跨次记忆主动开口（unprompted-from-memory）

> 这是产品的杀手时刻，也是 §5.2 唯一的真护城河（用户私有记忆飞轮）的具体落点。这个模式做得有多扎实，护城河就有多扎实。

#### 3.10.1 触发条件（严格门槛）

`SHOULD_INITIATE_FROM_MEMORY(state)` 必须全部为真：

```
Memory.status == warm                                  
    AND Memory.match_count >= 1                                  
    AND Memory.match[i].similarity_score >= 0.75              
    AND Memory.match[i].similarity_type ∈ {style_lineage, dwell_correspondence, user_phrase_recall}
    AND Dwell ∈ {mid, long, lingering}                        
    AND Audio != Speaker_NoisyEnv                            
    AND TimeSinceLastInitiate >= 15min                         
    AND UserInitiateRatio_Today >= 2.0                          
    AND NOT MatchCooldown.active(matched_artifact_id)         
```

任何一条不满足 → 沉默，**且不重试**（不要等 30 秒再问 SHOULD_INITIATE，会让用户感到 agent 在围着自己等机会）。

#### 3.10.2 信息层次

只有 1 层。这是个**单次主动开口**，不是开启一段对话。

> 多说一句都会破坏 wow——用户需要时间消化。

#### 3.10.3 输出形态

- 屏：屏幕主动从黑底亮起一次，居中单句话，3 秒后自动柔光褪色。
- 耳机模式：低音量耳语一句。
- **不出现追问 UI**——卡片上没有"想聊聊吗？"按钮。用户要继续，得自己主动。

#### 3.10.5 例外条款：≥ 3 次跨馆触发后允许加一句轻追问

跨次记忆模式默认**不追问**——让用户自己决定要不要接话。但是当 agent 已经成功触发过该用户的跨次记忆 ≥ 3 次（即用户已经体验过几次"它真懂我"），允许在主动开口尾部加一句 ≤ 8 字的轻追问，例如"要不要先看？"。

理由：前 3 次必须用沉默换信任；信任建立后用户希望 agent 更主动一点，但仍保持 ≤ 8 字的礼貌门槛。

这条规则把"产品价值随使用时长复利"（§5.2 真护城河）落到具体行为——**agent 对老用户和新用户应当不一样**。

#### 3.10.6 失败兜底

| 失败模式 | 后果 | 处理 |
| --- | --- | --- |
| 锚点不足 2 个 | wow 时刻会变成"说了句没营养的话" | 静默，不输出 |
| 记忆字段被推断（例如时间从"今年"被 LLM 演成"今年 3 月"） | 用户察觉造假 → 信任崩塌 | LLM 输出必经"锚点验证器"：每个锚点须能在 memory payload 里精确字符串匹配，否则该次输出被丢弃 |
| 用户对此次开口无响应（30 秒沉默） | 可能是 wow 也可能是冒犯 | 不重试。下一次满足条件至少要再等 15 分钟（§7.4.2 频率上限） |
| 用户开口后给负反馈（"你这是监控我？"） | 信任问题升级 | 触发隐私 reassurance 模式（待 v1 设计），并把该用户的 MemoryInitiateRatio 上限从 0.5 降到 0.2 |

#### 3.10.7 度量

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| memory_initiate_count_per_visit | 单次参观主动跨次记忆开口次数 | ≤ 2 |
| memory_initiate_user_engaged_rate | 主动开口后用户在 60 秒内有响应的比例 | ≥ 60% |
| memory_initiate_user_negative_rate | 主动开口后用户给负反馈的比例 | ≤ 5% |
| anchor_verification_pass_rate | LLM 输出通过锚点验证器的比例 | ≥ 95%（低于即说明 prompt 失控） |

### 3.11 深抠模式 B · M-06 四卡观点对照（layered-disclosure）

> 这是"信息分层"最显性的模式——4 张卡 = 4 个声音的层级化展开。

#### 3.11.1 触发条件

用户主动点击当前卡片的「我的看法」标签。**纯用户触发**，agent 不预测、不推荐。

#### 3.11.2 信息层次（4 层，固定顺序）

| 卡 | 角标 | 内容来源 | 信息密度 | 用户行动 |
| --- | --- | --- | --- | --- |
| 1 | 你刚才说 | user_state（用户原话 / emoji） | 极低（1 个词组） | 自动展示 |
| 2 | 馆方解读 | museum_labels API（上博官方标签） | 中（≤ 60 字压缩） | 横滑进入 |
| 3 | 我的看法 | RAG + LLM 生成，必须含"我倾向"立场词 | 中（≤ 60 字） | 横滑进入 |
| 4 | 学界争议 | RAG（is_disputed=true）+ 强制四要素引用 | 高（默认 ≤ 80 字；展开后 ≤ 300 字论文摘要） | 横滑进入 → 长按展开 |

**为什么顺序是用户 → 馆方 → AI → 学界**：

- 用户在第一张 = 把对等姿态从话术兑现成 UI 排序（§4.4 产品灵魂"把你当同侪"的兑现）
- 馆方在 AI 之前 = 不挑战馆方（§12.5.3 馆方博弈的落地）
- 学界在最后 = 留给愿意往深走的用户，不打扰其他用户

**这就是"信息分层"的具体落法**：层级不是"折叠 / 展开"的视觉花活，是**信息源的排序权**。

#### 3.11.3 输出形态

横滑卡片堆叠（不是表格、不是 tab）。每张卡黑底单句，左上角小角标标识来源。

四列表格在手机竖屏上视觉不成立，单屏宽度只够 2 列舒适阅读——这是从 §8.2 第 2 条"零滚动、零层级、展开靠切卡"反推的硬约束。

#### 3.11.4 追问入口形态（每张卡不同）

| 卡 | 追问入口 | 形态 |
| --- | --- | --- |
| 1 | 「补充一句」 | 文字 / 语音输入 |
| 2 | 「为什么这么说」 | 进入 M-07 学界引述 |
| 3 | 「为什么这么觉得」 | AI 给出更详细的观察依据（≤ 100 字） |
| 4 | 「看摘要」 | 展开论文摘要（≤ 300 字 / 篇）+ 「保存到今晚」按钮 |

每张卡只有一个追问入口——不要让用户在卡上选择多种动作。这是把"零层级"落到追问设计。

#### 3.11.6 信息分层的"密度递增"原则

四卡按顺序信息密度递增：低 → 中 → 中 → 高。这是设计选择：

- 用户在卡 1 / 卡 2 退出（看到自己 + 馆方），就够了——满足了"轻型用户"。
- 用户滑到卡 3，多看 AI 一眼立场——满足了"愿意听 AI 但不愿读论文"的用户。
- 用户滑到卡 4 + 长按展开，进入论文摘要——满足了深度用户。

这个设计兑现了 §3.2 中"中度爱好者光谱"的多层服务：**同一个模式同时服务 3 种使用深度**，不是分版本，是分层卡。

#### 3.11.7 失败兜底

| 失败模式 | 后果 | 处理 |
| --- | --- | --- |
| RAG 未命中学界争议但 LLM 编一个 | 信任崩塌 + 业内人打脸 | 强制 citation 字段校验：所有引用必须能在 RAG 返回的 retrieved_context 里精确字符串匹配作者 + 年份。无法匹配则卡 4 整张退化为 "没什么大争议" 模板。|
| 卡 3 否定了卡 2（如"馆方写错了") | 违反 §12.5.3 馆方关系约束 | 后过滤：如果卡 3 含 "馆方错" / "不对" / "不准确" 等词，强制改写为 "馆方的判断是 X，我倾向补充一个角度：Y" |
| 卡 3 stance_strength 标为 strong 但 RAG 证据不足 | AI 装权威 | LLM 输出后再过一层 stance 评估器：仅在 RAG 命中 confidence==high 时允许 strong；否则降级。|
| 用户只滑到卡 1 就关掉 | 没事，本来就允许 | 不算失败。但记录滑动深度作为度量。|

#### 3.11.8 度量

| 指标 | 含义 | 目标 |
| --- | --- | --- |
| swipe_depth_mean | 用户平均滑到第几张 | ≥ 2.5（即多数用户至少看了 AI 立场） |
| card4_expand_rate | 看到卡 4 的用户中点击"看摘要"的比例 | ≥ 20%（验证学界争议层是真有人看） |
| citation_verification_pass_rate | 卡 4 引用通过校验的比例 | ≥ 99% |
| ai_view_negation_post_filter_rate | 卡 3 被后过滤改写的比例 | ≤ 3%（高于即 system prompt 失控） |

### 4.2 Agent 视图（单轮 Agent Loop）

每一轮 agent 收到事件后的内部决策。这是"agent 怎么主导"的核心——**它每一轮都要做 5 件事**：

```
┌──────────────────────────────────────────────────────────────┐
│                    每一轮 Agent Loop                           │
├──────────────────────────────────────────────────────────────┤
│                                                                │
│  1. 感知（Perceive）                                            │
│     │                                                          │
│     ├─ 系统事件: location 变化 / dwell tick / audio route /    │
│     │           pickup gesture / 麦克风分贝 / 倒计时结束       │
│     ├─ 用户输入: 文字 / 语音 / emoji / 按钮点击 / 静默 30s     │
│     └─ 内部 tick: 15min 节奏检查 / promise fulfill_when 评估   │
│                                                                │
│  2. 状态更新（Update State）                                    │
│     │                                                          │
│     └─ 把事件 reduce 到 6 维状态                                │
│        (Location, Dwell, Audio, Promise, Memory, Fatigue)      │
│                                                                │
│  3. 选模式（Dispatch Pattern）                                  │
│     │                                                          │
│     └─ 决策树（见 §4.3）：当前状态 + 事件 → M-XX 或 SILENT     │
│        SILENT 也是一个合法的"行动"，不是 fall-through         │
│                                                                │
│  4. 组装 Prompt + 调工具（Assemble）                            │
│     │                                                          │
│     ├─ 取人格基础块                                            │
│     ├─ 注入当前 STATE 字段                                    │
│     ├─ 按模式调对应工具:                                       │
│     │   ├─ M-02/03/06/07 → rag.fetch(current_artifact)        │
│     │   ├─ M-04          → memory.fetch_matches(user_id, ctx) │
│     │   ├─ M-03 fulfill  → promise_queue.fetch_ready()        │
│     │   └─ M-08          → session_state.summarize()           │
│     ├─ 注入 RAG / memory 结果                                  │
│     └─ 注入模式专属 few-shot                                   │
│                                                                │
│  5. 生成 + 后过滤（Generate + Filter）                          │
│     │                                                          │
│     ├─ LLM 生成                                                │
│     ├─ 字段校验器（M-04 锚点匹配 / M-06 citation 校验）       │
│     ├─ 6 准则 enforcement（禁词 / 字数 / 立场词 / 句式）       │

│                                                                │
```

### 4.3 选模式决策树

```
事件 + 当前状态
       │
       ▼
┌─────────────────────┐
│ 是 location 转换？  │── 是 ── M-01（recognition）
└──────┬──────────────┘
       │ 否
       ▼
┌─────────────────────┐
│ promise_queue 中    │
│ 有 fulfill_when 命中？│── 是 ── M-03 兑现（→ M-02 变体）
└──────┬──────────────┘
       │ 否
       ▼
┌─────────────────────┐
│ 是用户主动事件？    │
└──────┬──────────────┘
       │ 是
       │
       ├── 点击「我的看法」 → M-06
       ├── 按下「合上手机」 → M-05
       ├── 文字 / 语音 / emoji 输入
       │   │
       │   ├── 第一次输入 → M-02
       │   ├── 含跨件大问题 → M-03
       │   ├── 含断代 / 风格问题 + RAG 命中 disputed → M-07
       │   └── 其他 → M-02 变体（继续对话）
       │
       └── 进入离馆 → M-08
       │
       │ 否（无用户事件）
       ▼
┌─────────────────────┐
│ SHOULD_INITIATE_    │
│ FROM_MEMORY(state)？│── 是 ── M-04
└──────┬──────────────┘
       │ 否
       ▼
   SILENT（什么都不做 = 合法行动）
```

> 注意：**SILENT 是 §4.3 这棵决策树的默认叶子**。任何分支没匹配上，agent 就什么也不做。这是把"默认沉默"落到 agent loop 的代码级表达。

### 4.4 Pattern × State 矩阵摘要

每个模式只在特定状态组合下才被允许触发。下表列出关键约束（完整组合在工程阶段展开）：

| 模式 | 必要状态 | 禁止状态 |
| --- | --- | --- |
| M-01 | Location 转换 | – |
| M-02 | Dwell ≥ short, 用户主动 | – |
| M-03 | 用户输入含 cross-artifact 问题 | – |
| M-04 | Memory == warm + Dwell ≥ mid + Audio != Speaker_Noisy + 各种频率约束 | Promise.pending（先兑现再说） |
| M-05 | 用户主动按下 | 任何 agent 主动 |
| M-06 | 用户主动点「我的看法」 | – |
| M-07 | 用户问 + RAG 命中 disputed | – |
| M-08 | Location → Outside OR Fatigue persisted | – |

## 5. 第三层 · Harness Spec

把 §3 的模式库 + §4 的 loop "跑起来"的上层编排系统。

### 5.1 上下文管理（Context Management）

#### 5.1.1 三层记忆系统

```
┌─────────────────────────────────────────────────────────────┐
│                     三层记忆                                  │
├─────────────────────────────────────────────────────────────┤
│                                                               │
│  Short-term（当前轮）                                         │
│  ─ 当前文物 retrieved_context（≤ 4k token）                  │
│  ─ 最近 3 轮对话原文                                          │
│  ─ 6 维状态当前值                                             │
│  ─ Lifetime: 单轮，下一轮重新组装                              │
│                                                               │
│  Session（当前参观）                                          │
│  ─ 参观路径（已看过的文物列表 + dwell）                       │
│  ─ 用户当次说过的原话（按文物索引）                            │
│  ─ Promise queue（pending）                                  │
│  ─ MatchCooldown 表                                          │
│  ─ Lifetime: 入馆 → 离馆 + 24h                                │
│                                                               │
│  Long-term（跨次记忆 · 真护城河）                              │
│  ─ 历次参观的 visit_session JSON                              │
│  ─ 每件文物的 dwell + user_quotes + 触发过的模式               │
│  ─ 用户偏好向量（风格脉络 / 时期 / 工坊偏好）                  │
│  ─ 已兑现 / 已过期承诺                                         │
│  ─ Lifetime: 永久（用户主动清除前）                            │
│  ─ 存储: 本地 SQLite + 用户主动开启时云同步                    │
│                                                               │
└─────────────────────────────────────────────────────────────┘
```

#### 5.1.2 上下文压缩策略

跨次记忆是真护城河，但 token 不是免费的。压缩策略：

| 数据 | 不压缩 | 压缩到 | 何时召回原文 |
| --- | --- | --- | --- |
| 用户原话 | ✓ 全保留 | – | 永远 |
| 单件 dwell | ✓ 保留分钟级 | – | 永远 |
| 文物元数据 | – | 仅保留 id + style_lineage 标签 | 通过 id 反查 |
| AI 历次发言 | – | 仅保留 pattern + 关键观点 1 句 | 一般不召回；除非用户问"你上次说过什么" |
| 路径数据 | – | 压缩为 enter/exit 时间 + 主要 hall | 不召回 |

跨次记忆召回是**用户原话 + dwell + 文物 id**的组合查询，不是全文检索——这让长期数据保持在每次参观 ~2-5KB 的尺度。

### 5.2 工具调度（Tool Orchestration）

#### 5.2.1 工具清单

| 工具 | 触发模式 | 异步 | 失败时降级 |
| --- | --- | --- | --- |
| `rag.fetch(artifact_id)` | M-02/03/06/07 | ✓ | 用 stub label，AI 输出降级到弱措辞 |
| `memory.fetch_matches(user_id, ctx)` | M-04 | ✓ | 直接返回 Memory==cold |
| `museum_labels.fetch(artifact_id)` | M-06 | ✓ | 缺卡 2 整张退化为"暂无标签" |
| `promise_queue.add / check` | M-03 创建 / 所有轮兑现检查 | 同步 | – |
| `state_machine.reduce(event)` | 所有事件 | 同步 | – |
| `enforcement.filter(output)` | 所有 LLM 输出 | 同步 | – |
| `anchor_verifier(output, memory_payload)` | M-04 后处理 | 同步 | 失败 → 静默 |
| `citation_verifier(output, retrieved_context)` | M-06 卡 4 / M-07 | 同步 | 失败 → 退化到 "没什么大争议" |

#### 5.2.2 预热（Eager Fetch）

用户在物理空间移动，agent 不能让用户"等响应"。蓝牙信标识别用户进入新展厅的瞬间，harness 预先：

1. `rag.fetch` 当前展厅前 5 件最可能被看的文物（基于历史 dwell 分布）
2. `memory.fetch_matches` 当前展厅风格脉络与用户长期记忆的潜在匹配
3. 把结果缓存到 session 内存

这样当用户在某件前停下后，对应 prompt assembly 几乎是 0 latency。

预热是把"工具是慢的"这个事实从用户感知里抹掉的关键。

#### 5.2.3 工具失败的统一姿态

任何工具失败时，agent 的姿态都是**承认不知道**，不是编造：

| 失败 | 输出 |
| --- | --- |
| RAG 全失败 | "这件我得查一下，咱们先看实物。" |
| Memory 失败 | 直接静默（不开口主动 wow） |
| Promise queue 错乱 | 不主动兑现（默认沉默） |

这是 §6.4 准则 5（诚实）落到工程兜底。

### 5.3 与通用 Agent SDK / Claude Code Harness 的对比

> 这一节是给作品集 reviewer 看的——证明作者懂通用 harness 长什么样，也懂这个垂直 harness 哪里不一样。

#### 5.3.1 相同之处

| 维度 | 共有特征 |
| --- | --- |
| 状态驱动 | 两者的核心都是 state → action 的循环，不是无状态 chat |
| 工具调度 | 两者都需要 LLM 决定调用哪个工具 + 处理结果 |
| 输出过滤 | 两者都在 LLM 输出后有一层校验 / 降级 |
| 上下文压缩 | 两者都面临 token 上限，都需要压缩历史 |

#### 5.3.2 关键不同

| 维度 | Claude Code Harness | 本产品 Harness |
| --- | --- | --- |
| **任务模型** | 单一会话内完成单一任务 | 长程多次会话，无明确终止 |
| **轮次触发** | 用户每轮都明确输入 | **多数轮没有用户输入**——agent 自决是否行动 |
| **主动性默认值** | 主动（"接下来我建议……"）| **沉默**（默认行动是不行动） |
| **工具语义** | 确定性（读文件、跑命令） | 模糊检索（RAG、记忆相似度） |
| **失败代价** | 错操作可能删错文件 | 错主动开口可能破坏信任 |
| **成功标准** | 任务完成 | 关系累积（用户记忆 + 信任）|
| **上下文范围** | 单次会话内 | **跨次（月级、年级）**，需独立的 long-term store |
| **模式池** | 通用（不区分领域） | **领域定制**（8 个模式都是博物馆场景特化） |
| **enforcement** | 主要在工具安全（不删文件） | **主要在人格 + 内容真实**（不说"您" + 不编引用） |

#### 5.3.3 本 harness 独有的设计抉择

1. **SILENT 是合法叶子节点**：通用 agent loop 里 fall-through 通常意味着 bug；本 harness 里 SILENT 是默认行为，需要显式条件才"行动"。
2. **预热 (eager fetch)**：通用 harness 假设响应时间是 OK 的；本产品物理场景下 latency 必须趋零，所以工具调用前置到位置变化时。
3. **锚点 / 引用验证器**：通用 LLM 应用允许"基于检索内容生成"；本产品对部分模式（M-04, M-06 卡 4）要求**精确字符串匹配验证**，验证不过就静默/降级。这是把幻觉容忍度压到 0 的工程化。
4. **三层记忆 + 跨次召回**：通用 SDK 不假设 cross-session memory；本产品的 long-term store 是它的核心资产。

#### 5.3.4 一个更大的论点

通用 Agent SDK / Claude Code 是横向通用 harness。本产品是**纵向垂直 harness**。纵向 harness 的价值不在"代码量大"，在**对场景的深刻理解被翻译成具体约束**——SILENT 默认叶子、锚点验证器、预热策略、信息分层 4 卡——每一个具体决定都对应一个 PM 对"主题知识对话"的洞察。

这是 AI PM 的 differentiator：不是会接 LLM，是**会为一个具体场景设计 harness**。
