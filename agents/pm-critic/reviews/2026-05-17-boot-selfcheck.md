## 主要问题(按严重度排序)

1. **【严重】4,466 张图 + 计划再扩到 ~10,000 张的图像下载,与 demo 切片利用率仅 1.97%。** 在 Curator 在场的世界里,这是会被 reject 的过早投资。最迟应该在第一批 200-500 张图测通"我能下载、我能映射、我能在 chunk 里指 image_local"之后,**立刻停下,先做 30 件展品的清单 + 朝代/材质过滤**,然后定向下载。

2. **【严重】PRD §14.5 列了 8 条「v1 写作前需明确的关键决策」,本周 closed 0 条。** Phase 1 应该聚焦在 D-1 至 D-8 的逐条 close,本周 100% 时间花在 §10 数据层的执行上。这是**方向漂移**——把"决策"延后,把"执行"提前。

3. **【中】docs/index.html 的形态学问题。** 它是数据浏览器(brwoser-style),不是 PRD §1 反对的"权威单向播报"的对立面。把它放在 README 顶部、且没有显式声明"这不是产品 demo,只是数据资产可视化"——会让读者产生**关于产品形态的错误第一印象**,这与 PRD §4.1 定位直接冲突。

4. **【中】商业故事 0 推进。** 本周没有任何 commit 触及 PRD §1 / §12.4 / 招聘官+投资人故事面。dashboard 顶层 KPI"商业论证段落存在 = 否"在本周后**依然为否**。Phase 1 的招聘官+投资人故事是这阶段最重 KPI,但被排到了所有事的后面。

5. **【中】README 顶部数据量(15,299 / 4,466 / 3 馆)被用作主要 selling point,但这暗示了一个错误的"产品价值 = 数据量"叙事。** 现存博物馆 App 比拼的就是数据量,「一起看」恰恰是要从这个轴跳出去的(见 PRD §5.1 二维定位矩阵的"右上空白象限")。在 README 这样放数字,等于把项目自己往左下押。

6. **【中】"无 LLM CLI 搜索"作为 selling point 的反向信号。** `66d9d23` commit message 主动强调"演示无 LLM 也能做有意义查询"——这在 AI PM 作品集上下文里**精确地拉低 AI taste**。它应该被 reframe 为"在 LLM 接入前,先用确定性 baseline 验证数据 schema 完整性"(完全相同的代码,完全不同的故事)。

7. **【轻】3 个工程脚本(extract / build_rag_chunks / search / build_gallery / download_images)各自能跑,但没有顶层 makefile / runbook 把它们串起来。** 一个独立 reviewer 想跑通整个 pipeline 需要拼命读 README——可以做一次小的 DevX 提升,但这不是 P0。

8. **【轻】sync-log 在团队尚未建立的 7 天里是空的(2026-05-17 才有第一条)。** 这一项不能事后追究——团队没建立时本来就不该有 sync——但它意味着本次 review 是**追溯性**而非**进程性**的。需要在 Critic+Curator 在场后,所有 commit 都先经过 inbox。
